2.What I have been working on

2.1   Open-source contributions to Namma Yatri (Haskell, production)

The work I am proudest of in a large unfamiliar codebase with maintainer review is my contribution to Namma Yatri, the open-source ride-hailing platform that runs in production across India. Between November 2025 and January 2026 I shipped three merged PRs into the org:

  • featnammayatri/nammayatri#13442 — Special-zone driver-payout scheduling system. A distributed, event-driven scheduler serving roughly 10,000 rides per day; cut driver payout latency from weekly cycles down to T+2 hours under production traffic.
  • featnammayatri/nammayatri#13452 — Exposed the resulting driver-payout state to the driver-app frontend through the API layer.
  • featnammayatri/shared-kernel#1108 — PaytmEDC payment-flow integration in the shared kernel: config management, checksum generation, API interaction. Went through several review iterations before merge.

The technically interesting one is #13442. Driver payouts for special-zone rides (airports, stations) are computed per-ride but were previously paid out only on a weekly batch cycle — a long latency for drivers, and operationally fragile when the batch failed. The new system schedules per-ride payouts at T+2 hours after ride completion, which means roughly 10,000 scheduled jobs in flight at any given moment under load. The constraints made the design non-trivial:

  • Exactly-once execution. A payout that fires twice is real money lost; a payout that never fires is a real driver not paid. The scheduler had to be exactly-once under broker restart, app restart, and partial-failure scenarios.
  • No latency on the ride-booking hot path. Scheduling a payout is a side-effect of completing a ride; the ride-completion API could not block on scheduling state.
  • Idempotent state transitions. A retry of the payout-fire call had to be safe; the same input must yield the same end state, not double-debit.

The shape I landed on is a Redis-backed delayed-job scheduler keyed on ride-id, with per-ride distributed locks taken at fire time and an idempotency token persisted before the actual payout call. The per-ride lock ensures only one worker fires a given payout even if two pick it up simultaneously, and the idempotency token means a retry after a partial failure is safe. Working on a Haskell codebase with no prior production Haskell experience, designing the failure model with the team, and getting to merge three times in a row, is the closest thing I have done to what this LFX project will involve — and it is the muscle I am leaning on for that reason.

2.2   Juspay — production infrastructure work

2.2.1   Identity and secrets on OpenStack + OpenBao

We replaced a heavy AWS KMS dependency with an in-house identity-and-secrets layer running on OpenStack VMs and OpenBao. A few design choices shaped most of what I built:

  • Identity derived from the network, not from a long-lived token. A VM authenticating to the broker presents an IMDS-attested claim — its identity is the network position the orchestrator placed it at, signed by the platform. There is no static credential on disk an attacker can steal. The broker validates the attestation and issues a short-lived RS256-signed token scoped to what that VM is allowed to read.
  • Shamir secret-sharing for the root key. No single broker node holds the full root; it is split into m-of-n shards distributed across the cluster, and reassembled in memory only when needed. A single compromised node yields no useful secret material.
  • HA via Raft. Brokers run a Raft cluster across availability zones, so the identity service tolerates N−1 broker failures without an outage — the same posture etcd or CockroachDB take, applied to secrets.
  • VM-side SDK in Python (osvault) for the bootstrap flow — handles attestation, token refresh, leasing, and audit. The broker itself is Go.

2.3   Independent project: PostgreSQL on Kubernetes / OpenStack

A 5-layer nested virtualization stack on a single i9-14900 box: bare-metal Linux at the bottom, KVM running an OpenStack tenancy on top, Kubernetes running inside that, CloudNativePG inside Kubernetes, Postgres inside CNPG. The work was equal parts performance tuning, lifecycle automation, and identity plumbing.

Performance tuning. The inner-VM Postgres saw write-TPS climb roughly 50% after two pieces of work — NUMA-aware CPU pinning of the Postgres workers to the same socket as the L1 hypervisor exposing the disks, and 16 GB of hugepages dedicated to the inner VM. The buffer pool was thrashing the TLB at default page sizes; 2 MB pages cut TLB misses enough that the syscall cost on every page fault went away.

Lifecycle automation. Cluster API for OpenStack (CAPO) provisions VMs declaratively; CloudNativePG is the Kubernetes operator that runs the Postgres cluster. End-to-end, a single kubectl apply brings up an HA Postgres cluster (one primary + N replicas, synchronous WAL streaming) in ~12 minutes from cold. Failover is automatic — CNPG runs a leader-election loop, demotes the failing primary, promotes a healthy replica, and rewires the service endpoint. Tested under primary-VM kill and primary-VM network partition; recovery to write-ready in roughly 7 seconds with RPO=0 (no acknowledged write lost, because the synchronous stream guarantees the standby has it before the primary acks the client).

Identity plumbing. A Go-based OpenBao broker plus the osvault Python SDK on the VM side delivers secrets at bootstrap — the VM proves its OpenStack-assigned identity via IMDS, the broker validates it, the SDK fetches the secrets it is allowed to.

2.4   urunc so far — what I have learned through issue #389

A few weeks ago I picked up urunc-dev/urunc#389 — high host CPU caused by console output in running containers. A prior contributor had attributed the regression to bufio.Scanner in cmd/urunc/log_forward.go. My own profiling showed that path is not hot during guest execution: that scanner only handles the parent-child JSON log pipe during urunc create; once syscall.Exec() runs the VMM manages stdio directly. The real cost lives one layer deeper.

I wrote a small KVM-exit and throughput sampler — bench-console.sh, which @ananos has since indicated they would like to fold into CI as a regression check — and traced the regression to per-byte PIO traps on the 16550 UART at port 0x3F8. The -serial stdio baseline costs roughly 1.16 M PIO exits per 5-second window, with QEMU's address_space_write dominating the host flame graph. A simple virtio-console swap drops PIO exits to ~0 and lifts throughput from 2,016 to 73,378 lines/sec (about 36×), closing the runc-vs-urunc gap on this workload from roughly 407× down to ~11×.

The thread has since covered: how to differentiate virtio-console from serial without breaking Linux kernels built without CONFIG_VIRTIO_CONSOLE (my first proposal, a capability-intersection design borrowed from the rootfs path, was constructively rejected by @cmainas for exactly that reason); the upcoming pivot from the com.urunc.unikernel.cmdline annotation to a kernelArgs-style annotation that lets users specify boot parameters at build time; and an invitation from @ananos to draft a blog post on the investigation for the CNCF blog.

Through that work I have gained working familiarity with:

  • Monitor invocation path — pkg/unikontainers/hypervisors/qemu.go, BuildExecCmd, and the syscall.Exec-style handoff in unikontainers.go.
  • The distinction between the parent-child JSON log pipe (consumed by bufio.Scanner before syscall.Exec) and the VMM-managed stdio path that takes over after.
  • The QEMU + KVM monitor surface — what costs PIO exits at the 16550 UART, how virtio devices change the picture, where the cost actually lives.
  • Linux unikernel path — pkg/unikontainers/unikernels/linux.go, the boot-params construction, the urunit handshake.
  • The VMM interface in pkg/unikontainers/types/types.go and how each monitor (QEMU, Firecracker, HVT) implements it today.
  • An empirical debugging posture — /sys/kernel/debug/kvm/io_exits, perf flame graphs, and a small reproducer image, rather than guessing.

3.The project — monitor lifecycle for urunc#112

3.1   The problem

urunc today shells out to QEMU or Firecracker with a long command string. That is enough to start a sandbox, but everything after that — checking what the guest is doing, hotplugging a device, asking the monitor to shut down gracefully, attaching a console after the fact — is either impossible or has to be approximated by signalling the host process. Once syscall.Exec hands off to the monitor at unikontainers.go:533, the only handle urunc retains is the PID. Both QEMU and Firecracker already expose proper socket APIs — QMP for QEMU, a REST-style API socket for Firecracker — and the slide deck for #112 calls out a secondary benefit: the reexec process currently blocks on AwaitMsg(StartExecve) between the create and start phases, and that gap can be used for parallel VMM init for a ~30 ms boot win.

3.2   Driving each monitor through its API end-to-end

Before writing the proposal I wanted to see what QMP and the Firecracker API actually look like in practice, not just in the docs. I wrote two small Go clients and drove each monitor through a real lifecycle.

The QMP run starts qemu-system-x86_64 8.2.2 paused with -S -qmp unix:<sock>,server,nowait and then walks through the greeting, qmp_capabilities, query-status, cont, query-cpus-fast, stop, quit. The whole exchange is around 2 ms on a local Unix socket. The non-obvious thing I learned: QMP interleaves async events with command replies on the same socket. My first version of the client was naive — one read per command — and it worked through the handshake, then cont's RESUME event arrived before the cont reply, every read after that was off-by-one, and query-cpus-fast's reply turned up where I was expecting stop's. The fix is to type-dispatch every frame: {return} or {error} is a reply to the most recent in-flight command; {event, timestamp, data} is async telemetry that goes to a separate subscriber. It is the kind of thing that does not surface from reading docs.

The Firecracker run is more involved because Firecracker has no CLI for guest config — only --api-sock. Background mode is the only mode it has. I drove the full lifecycle through the API: GET / to read the instance info, PUT /machine-config with 1 vCPU and 128 MiB, PUT /boot-source with the kernel path and cmdline, PUT /drives/rootfs with an Ubuntu 22.04 ext4 image, PUT /actions {InstanceStart} to boot, GET / to verify the state moved to Running, PATCH /vm {Paused} and {Resumed} to exercise pause and resume, and finally PUT /actions {SendCtrlAltDel}. The microVM booted, reached systemd, honored the Ctrl-Alt-Del, and Firecracker exited with exit_code=0. The only call that took meaningful time was InstanceStart at 16 ms — the actual KVM boot. Everything else was 0.3–0.5 ms. Three things contrast with QEMU and matter for the interface design: FC has no CLI for guest config, no async events on the socket, and no device_add equivalent — you can PATCH existing drives but cannot attach a new device after boot.

After both wire flows checked out I wanted to verify the same thing against a real running Linux guest, not just a paused dummy. I started QEMU with the same -S -qmp setup plus an Ubuntu cloud image attached, sent cont, waited for the guest to boot (Ubuntu 5.15 came up cleanly through SeaBIOS and iPXE), then exercised the lifecycle ops on the running guest: stop and cont to pause and resume, query-block to read the attached qcow2 path, query-cpus-fast for vCPU thread IDs, netdev_add and device_add to hotplug a virtio-net-pci on the fly, query-pci to confirm it appeared, device_del to unplug, and finally quit for a clean shutdown.

One urunc-relevant detail surfaced from this last run that I would have missed otherwise. My first hotplug attempt failed with Bus 'pcie.0' does not support hotplugging. q35 — the default machine type on modern QEMU, and what urunc's qemu.go uses today since it does not specify -M for x86_64 — exposes the root PCIe bus as pcie.0, which is not hotplug-capable. To hotplug PCIe devices the QEMU command line has to pre-allocate one or more pcie-root-port devices at startup, and device_add then targets the root port via bus=rp1. I added -device pcie-root-port,id=rp1,chassis=1,slot=1 to the QEMU args and the hotplug worked. The actual device_add took ~11 ms — real PCI enumeration, the same order of magnitude as Firecracker's 16 ms InstanceStart.

The transcripts and run scripts are in this repo under prototypes/ for anyone who wants to reproduce the runs.

3.3   My approach — invert the timing, keep everything else

The smallest change to urunc's existing flow that achieves what #112 wants is to invert the timing of the existing execve and have the monitor start paused. Concretely, in unikontainers.go:533 the reexec process currently calls syscall.Exec only after urunc start has signalled StartExecve; the monitor then immediately runs the guest. Move the execve earlier — right after CreateContainer hooks — and have BuildExecCmd produce a paused command (QEMU's -S -qmp unix:<sock>,server,nowait, Firecracker's --api-sock <sock> with no boot action yet). Reexec is gone the moment execve returns. The monitor process is now alive, paused, listening on its API socket. urunc start then connects to that socket and sends the "start guest" command (cont for QMP, PUT /actions {InstanceStart} for FC), verifies the state, runs Poststart hooks, and exits.

What this preserves:

  • containerPid == monitor PID. Same as today. The shim, containerd, the OCI hooks, the pid-file — none of them see a different process model.
  • The execve handoff and the namespace inheritance. CreateContainer hooks still run in reexec before execve; the monitor inherits the same namespaces from the same call. No new code path.
  • The VMM interface in pkg/unikontainers/hypervisors/types.go. Same shape, extended with the post-spawn operations urunc needs — probe state, pause, resume, shutdown, hotplug net/block, attach console — and a capability flag for backends that lack a socket (HVT keeps the current CLI-only path).

What this changes:

  • The existing urunc IPC handshake becomes vestigial. StartExecve and StartSuccess on urunc.sock exist today to coordinate reexec and urunc start across the gap. With the monitor paused on its own socket, the verification urunc start needs is "is the monitor socket responsive?" — which is a stronger check than the current "we assume the execve succeeded." The IPC sockets can be removed cleanly.
  • The parallel-init opportunity falls out for free. Between reexec's execve and urunc start's cont, the monitor is doing device emulation setup, kernel-image loading, virtio queues — exactly the work the slide deck targets. The Firecracker probe puts a number on it: only PUT /actions {InstanceStart} costs real time (16 ms); every config call is sub-millisecond, and all of them happen before the start command lands.
  • Lifecycle ops after start (urunc kill, urunc delete, future urunc state or urunc attach) connect fresh to the persisted socket, send the operation, close. Per the QMP probe, that round-trip is sub-millisecond. Fallback when the socket is dead is signal-to-PID, exactly as today.

Both prototypes in §3.2 already validate this exact flow on the wire side: the QMP probe starts QEMU with -S and sends cont; the Firecracker probe starts FC with --api-sock only and sends PUT /actions {InstanceStart} via the API. The urunc-side code change — moving where in reexec the execve happens, removing the urunc IPC handshake, teaching urunc start to talk to the monitor socket — is real work, but it is well-scoped and doesn't introduce any new process-lifetime concepts.

The alternative I considered was a long-running supervisor process that owns the monitor and the persistent socket connection. I think that is the wrong direction here. It changes containerPid semantics (the supervisor becomes the container's init process, not the monitor itself), introduces a new zombie state (live supervisor + dead monitor), and the persistent-connection benefit it provides is small — Unix-socket reconnect is sub-millisecond per the QMP probe, and async-event subscription is the only thing that genuinely benefits, which can be a separate event-sink process rather than the container's init. The invert-the-timing approach above does more with less.

3.4   Concrete changes in code

  • pkg/unikontainers/hypervisors/qemu.go — BuildExecCmd adds -S -qmp unix:<sock>,server,nowait and pre-allocates one or more pcie-root-port devices at startup (-device pcie-root-port,id=rp1,chassis=1,slot=1) so hotplug works on the default q35 machine — without this, every device_add fails with Bus 'pcie.0' does not support hotplugging, which is the kind of thing that does not show up until you actually run it. Implement the new control methods for QMP: query-status (probe), quit (replaces the current killProcess in Stop), cont/stop (pause/resume), device_add/device_del (hotplug for virtio-net and virtio-blk first, targeting bus=rp1), chardev-add/chardev-remove (console attach/detach). Wire types hand-rolled from the prototype.
  • pkg/unikontainers/hypervisors/firecracker.go — BuildExecCmd moves to --api-sock <sock>-only. The existing per-VM config (machine-config, boot-source, drives, network) moves out of BuildExecCmd and into a "configure" step that runs against the API socket between execve and urunc start. Implement the same control methods via firecracker-go-sdk, with capability flags marking the differences (no device_add, no async events).
  • pkg/unikontainers/hypervisors/types.go — extend the VMM interface with the new control methods plus a capability-flag method (SupportsMonitorControl() or similar, in the same shape as the existing SupportsSharedfs). HVT and any future no-socket monitor return false and keep the current CLI-only path.
  • pkg/unikontainers/unikontainers.go — Exec (currently ending at syscall.Exec on line 533) now builds the paused command and execves into the monitor without waiting for StartExecve. The SendMessage(StartSuccess) at line 519 is removed; verification moves to urunc start's socket-connect.
  • cmd/urunc/create.go — the reexec branch (line 347 onward) no longer creates the urunc.sock listener or waits on AwaitMsg(StartExecve). After CreateContainer hooks it falls straight through to unikontainer.Exec.
  • cmd/urunc/start.go — instead of sending StartExecve via the urunc IPC, opens a connection to the monitor's API socket (path read from state.json), sends the configure-and-start sequence (cont for QEMU; the FC config PUTs followed by InstanceStart for FC), verifies state, runs Poststart. The connect uses the same retry-with-backoff pattern sendIPCMessageWithRetry in pkg/unikontainers/ipc.go already uses for urunc's own sockets — the monitor may not have its socket up immediately after execve.
  • cmd/urunc/kill.go, cmd/urunc/delete.go — attempt graceful shutdown via the API socket (QMP quit, FC SendCtrlAltDel) first; fall back to signal-to-PID when the socket is unresponsive.
  • pkg/unikontainers/ipc.go — the StartExecve/StartSuccess/StartErr message types and the urunc.sock/reexec.sock plumbing become unused. Remove them in a separate clean-up PR after the new path is the default. The sendIPCMessageWithRetry helper itself is still useful — urunc start uses it for the monitor socket connect.

3.5   Out of scope and what I will verify

Out of scope for this LFX even if time allows: rewriting urunc's seccomp handling (PreExec for HVT), adding a third monitor (cloud-hypervisor, Dragonball — the interface should make it easier, but doing it is somebody else's first PR), introducing a heavy QMP or FC client library when the prototypes already show both wires are small enough to hand-roll, and rewriting the existing reexec/urunc-start IPC channels.

Before each merge I commit to verifying: the QMP-controlled QEMU path can spawn paused, query state, gracefully shut down, and hotplug a virtio-net device end-to-end with the existing nginx-on-unikraft integration tests staying green; the Firecracker path can do the equivalent subset; the CLI-only fallback continues to work for HVT and any monitor that does not expose a socket; an extended bench-console.sh measures per-round-trip cost on both backends and lands in CI as a regression check.
